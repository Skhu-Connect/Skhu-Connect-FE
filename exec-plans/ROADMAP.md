# 실행 로드맵

**이 파일은 목차다.** 실행 항목은 아래 5개 파일에 있다.
원래 한 파일이었고 559줄이 되면서 쪼갰다.

| 파일 | 대상 | 상태 |
|---|---|---|
| [roadmap-web.md](roadmap-web.md) | 학생 웹 6화면 + **공용 Foundation** | 완료 · 배포됨 |
| [roadmap-admin.md](roadmap-admin.md) | 관리자 콘솔 4화면 + 답변 모달 | 완료 · 배포됨 |
| [roadmap-ios.md](roadmap-ios.md) | iOS 앱(Expo/React Native) 5화면 | M0 완료, M1~M3 남음 |
| [roadmap-android.md](roadmap-android.md) | 안드로이드 | 계획 없음(범위 밖) |
| [roadmap-api-spec.md](roadmap-api-spec.md) | **전 화면 Figma 보드 + 백엔드 전달용 API 명세서** | F0·F1·A0·A1·A2 검증 완료, 전달만 남음 |

## 어디에 무엇이 있나

**Foundation 은 웹 문서에 있다.** 토큰·`Icon`·DS 프리미티브 14종·`src/api/`·zustand 스토어·
라우터 셸은 학생 웹과 관리자 콘솔이 같이 쓴다. 관리자 콘솔은 별도 앱이 아니라 같은 Vite
빌드 안의 `/admin` 경로이므로, **검증(Phase 3)과 배포(Phase 4)도 웹 문서 하나에 있다.**
관리자 문서에는 관리자 고유 화면(Phase 2)만 있다.

**iOS 는 코드를 공유하지 않는다.** 번들이 분리돼 있어 `src/api/` 를 재사용할 수 없고
목데이터를 `ios/src/data.ts` 에 따로 둔다. 공유되는 것은 디자인 토큰 값과 컴포넌트 수치뿐이다.
그래서 iOS 문서는 자체 Foundation(Phase M0)을 따로 갖는다.

**안드로이드는 별도 코드베이스가 아니다.** `ios/` 의 Expo 앱이 크로스 플랫폼이고
`app.json` 에 안드로이드 블록이 이미 있다. 그 문서는 실행 항목이 아니라 착수 전 확인 목록이다.

## 읽는 법

체크 표시는 "구현했다"가 아니라 **"완료 조건을 확인했다"**는 뜻이다. 각 항목의 `완료:` 줄이
그 조건이고, 확인 근거는 문서 안의 검증 기록 절에 남긴다.

## 이슈 분할

### 브랜드 로고 통일

**모든 로고 자리를 원본 이미지 한 장으로 통일한다.** 둥근 사각형 PNG(남색 `#1D1F52` 바탕,
말풍선 두 개 + 이중 체크)이고, 지금 화면마다 흩어져 있는 "청" 글자 타일과 모바일의 막대 3개 마크,
기본 Expo 아이콘을 전부 이 이미지로 바꾼다. 새 기능이 아니라 에셋 한 벌을 표면마다 붙이는 일이라
빌드 대상으로 나눈다 — 웹 번들과 모바일 앱은 런타임·에셋 규격·확인 방법이 다르다.

- **[CHORE] 웹·관리자 화면 브랜드 로고 이미지로 교체** — 선행 없음
  - 대상: `public/` 로고 PNG 추가와 `index.html` 파비콘 링크, `src/components/web/Header.jsx` 34px 타일,
    `src/pages/web/LoginScreen.jsx` 52px 타일, `src/layouts/AdminLayout.jsx` 34px 타일
  - 관리자 콘솔은 같은 Vite 빌드의 `/admin` 경로라 파비콘을 학생 웹과 공유한다. 그래서 쪼개지 않는다
  - 완료: 세 화면과 브라우저 탭에서 "청" 타일이 사라지고 로고 이미지가 보인다. `public/favicon.svg` 참조가 남지 않는다
- **[CHORE] 모바일 앱 로고와 앱 아이콘 브랜드 이미지로 교체** — 선행 없음
  - 대상: `ios/src/screens/Login.tsx` 의 `LogoMark`(막대 3개 + 마젠타 점, 쓰이는 곳은 로그인 화면뿐),
    `ios/assets/` 의 `icon.png`·`favicon.png` 재생성(스플래시도 `icon.png` 를 그대로 쓴다), `ios/app.json` 스플래시 배경 `#34348A` → `#1D1F52`
  - 완료: 로그인 화면·앱 아이콘·스플래시가 모두 같은 로고다. 기본 Expo 파란 "A" 아이콘이 남아 있지 않다

안드로이드 적응형 아이콘(`android-icon-*.png`)은 범위 밖이다 — [roadmap-android.md](roadmap-android.md) 와 같다.

### 로그인할 때 소속 학부 받기

**로그인 폼에서 학생이 소속 학부를 직접 고르게 한다.** `POST /auth/login` **요청**에 `dept` 를 실어 보내는 일이고,
표시 쪽은 손대지 않는다 — `user.dept` 는 이미 아바타 드롭다운(`src/components/web/Header.jsx:175`)·
설정 모달(`src/components/web/SettingsModal.jsx:62`)·마이 화면(`ios/src/screens/My.tsx:39`) 세 곳에서 렌더된다.

로고 작업과 같은 축으로 쪼갠다 — 웹 번들과 모바일 앱은 런타임도 데이터 계층도 다르다(웹은 `src/api/` + zustand 스토어,
모바일은 `ios/src/data.ts` 상수). 로그인 화면이 런타임마다 하나씩이라 화면 기준으로도 둘이다.
API 계약(`dept` 필드 추가·검증 여부)은 백엔드가 별도로 관리한다 — 프런트에서 명세 문서를 만들지 않는다.

**학부 11개가 전부 목록에 들어간다.** 교육과정이 두 벌이고 재학생이 양쪽에 걸쳐 있다.
2024학년도 입학생부터 7개 — 인문융합콘텐츠학부 · 경영학부 · 사회융합학부 · 미디어콘텐츠융합학부 ·
미래융합학부 · 소프트웨어융합학부 · 국제학부.
2023학년도 입학생까지 4개 — 인문융합자율학부 · 사회융합자율학부 · 미디어콘텐츠융합자율학부 · IT융합자율학부.
출처는 학교 교무처 교무팀 페이지다. 이름을 줄이거나 바꾸지 않는다.

청원 카테고리 `department`(라벨 `학부`)는 청원 **주제**이지 학부 목록이 아니다 — 그 열거값을 재사용하지 않는다.
`user.dept`(소속 학부)와 `answer.dept`(답변 부서명, `학생지원팀` 등)도 다른 값이다. 폼 값과 응답 값이 다를 때는
**응답이 이긴다** — 표시 세 곳은 계속 응답의 `user.dept` 를 쓰고, 요청의 `dept` 는 서버가 참고하는 값이다.

- **[FEAT] 웹 로그인 화면에 소속 학부 선택 입력 추가** — 선행 없음
  - 대상: `src/pages/web/LoginScreen.jsx` 폼, `src/stores/session.js` 의 `login`, `src/api/index.js` 의 `login(sid, password)` 시그니처, 목데이터 `src/api/mockDb.js`
  - 새 컴포넌트를 만들지 않는다 — DS 에 `Select`(`src/components/ui/index.jsx:277`)가 이미 있고 `options` 에 문자열 배열을 받는다
  - 폼이 `FormData` 기반 비제어인데 `Select` 는 `value`·`onChange` 제어형이다. `name="dept"` + 네이티브 `required` 로 갈지 `useState` 로 올릴지는 이 이슈에서 정한다
  - 관리자 콘솔에는 로그인 화면이 없다 — 목 관리자라 세션을 쓰지 않는다(`src/stores/session.js` 첫 주석). 그래서 웹은 화면 하나다
  - 완료: 학부를 고르지 않으면 로그인 제출이 막히고, 고른 값이 `api.login` 인자로 넘어간다. 아바타 드롭다운·설정 모달의 학부 표시는 전과 같다
- **[FEAT] 모바일 로그인 화면에 소속 학부 선택 입력 추가** — 선행 없음
  - 대상: `ios/src/screens/Login.tsx` 폼, `ios/App.tsx` 의 `onLogin`, `ios/src/screens/My.tsx` 의 학부 표시, 목데이터 `ios/src/data.ts` 의 `USER`
  - 여기도 새 컴포넌트가 없다 — `ios/src/ui.tsx:216` 의 `Select` 가 `options: string[]` 를 받는 시트형 피커다
  - 학부 11개 배열은 웹과 **중복해서 둔다.** 번들이 분리돼 공유가 안 되고(위 "iOS 는 코드를 공유하지 않는다"), 문자열 11개를 나누려고 공유 장치를 만드는 게 더 비싸다
  - iOS 는 API 계층이 없어 로그인 응답이 없다. 고른 값이 화면에서 확인되려면 `onLogin` 이 학부를 받아 `MyScreen` 까지 전달돼야 한다 — `MyProps` 에 필드 하나 추가하는 수준이다
  - **목데이터가 안 맞는다** — `ios/src/data.ts:211` 의 `USER` 는 `sid: "202214139"`(2022 입학 = 구 교육과정)인데 `dept` 가 `"소프트웨어융합학부"`(2024학년도부터)다. 로그인 화면 기본 학번(`ios/src/screens/Login.tsx:21`)도 같은 값이라 기본 선택은 `IT융합자율학부` 가 맞다. 웹 `src/api/mockDb.js` 는 `sid: "20260000"` 이라 어긋나지 않는다
  - 완료: 로그인 화면에서 학부를 고를 수 있고, 고른 값이 마이 화면 프로필 줄에 그대로 보인다

**기록해 둘 결정 — 학생이 고른 학부는 검증되지 않은 값이다.** 종합정보시스템이 이미 학생의 학부를 알고 있고
로그인 **응답**에도 `user.dept` 가 실려 온다. 그런데도 학생이 직접 고르게 하면 그 값은 자기 신고다.
지금은 무해하다 — 임계치 산정은 모든 카테고리 `basis` 를 **전체 학생**으로 통일하고 "학부·기숙사도 예외 없다"고
이미 정해 뒀으므로, `dept` 는 임계치 계산에 들어가지 않고
권한도 필터도 가르지 않는다. **`dept` 에 권한이 생기는 순간**(학부별 임계치, 학부 한정 청원, 학부별 필터)
이 결정을 다시 봐야 한다. 그때는 폼 값을 버리고 서버가 아는 값만 쓰는 게 맞다.
