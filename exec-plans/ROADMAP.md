**이 파일은 목차다.** 실행 항목은 아래 4개 파일에 있다.
원래 한 파일이었고 559줄이 되면서 쪼갰다.

| 파일 | 대상 | 상태 |
|---|---|---|

| [roadmap-admin.md](roadmap-admin.md) | 관리자 콘솔 4화면 + 답변 모달 | 완료 · 배포됨 |

## 어디에 무엇이 있나

**Foundation 은 웹 문서에 있다.** 토큰·`Icon`·DS 프리미티브 14종·`src/api/`·zustand 스토어·
라우터 셸은 학생 웹과 관리자 콘솔이 같이 쓴다. 관리자 콘솔은 별도 앱이 아니라 같은 Vite
빌드 안의 `/admin` 경로이므로, **검증(Phase 3)과 배포(Phase 4)도 웹 문서 하나에 있다.**
관리자 문서에는 관리자 고유 화면(Phase 2)만 있다.

**iOS 는 코드를 공유하지 않는다.** 번들이 분리돼 있어 `src/api/` 를 재사용할 수 없고
목데이터를 `ios/src/data.ts` 에 따로 둔다. 공유되는 것은 디자인 토큰 값과 컴포넌트 수치뿐이다.
그래서 iOS 문서는 자체 Foundation(Phase M0)을 따로 갖는다.

**안드로이드는 별도 코드베이스가 아니다.** `ios/` 의 Expo 앱이 크로스 플랫폼이고
`app.json` 에 안드로이드 블록이 이미 있다. 그 문서는 실행 항목이 아니라 착수 전 확인 목록이다.

## 읽는 법

체크 표시는 "구현했다"가 아니라 **"완료 조건을 확인했다"**는 뜻이다. 각 항목의 `완료:` 줄이
그 조건이고, 확인 근거는 문서 안의 검증 기록 절에 남긴다.

## 이슈 분할

### 소속 학과 변경 API 연동 (2026-08-11)

**목표** — 로그인한 학생이 웹과 iOS의 MY 화면에서 소속 학과를 선택·저장하고, 성공 뒤 서버에서 다시 읽은 학과명이 즉시 표시된다.

- [ ] **계약·의존** — 프로덕션 Swagger의 `PATCH /connect/users/me/department`는 bearer 인증과 `{ "departmentId": number }`를 요구하고 성공 시 `204`만 돌려준다. 따라서 두 클라이언트는 기존 `GET /connect/departments`의 id를 보내고, 성공 뒤 `GET /connect/users/me`으로 화면 세션을 갱신한다. 인증되지 않은 요청의 `401`은 확인했으며, 웹·iOS 코드는 공유하지 않아 서로의 구현을 막지 않는다.
- [ ] **순서·검증** — 웹을 먼저 구현해 기존 선택 UI의 로컬 전용 갱신을 서버 갱신으로 교체하고, iOS는 같은 계약으로 MY 화면에 선택 UI를 추가한다. 각 이슈는 인증된 사용자로 A 학과 선택 → `204` → `GET /me`의 B 학과명 및 화면/재진입 표시를 확인하고, `400`·`404`·네트워크 실패에서는 성공 문구나 표시값을 확정하지 않는다.
- [ ] **재검토** — 공용 클라이언트·새 의존성·백엔드 작업은 추가하지 않는다. 이미 배포된 API와 각 앱의 기존 `GET /connect/departments`, 인증 재시도, 선택 UI를 재사용한다.

### 회원가입 약관·개인정보 안내 펼침 토글 (2026-08-11)

**목표** — 회원가입 2단계(계정 정보 입력)에서 약관·개인정보 안내가 기본으로 접혀 있고, 사용자가 화살표를 눌러 웹과 iOS 어디서든 같은 모양·같은 동작으로 펼쳐 읽은 뒤 동의할 수 있다.

- [ ] **계약·의존** — 백엔드 계약은 그대로다. `signup()`이 보내는 `termsAgreed`·`termsVersion`, 동의 없이 제출했을 때의 기존 문구("회원가입을 진행하려면 이용약관에 동의해주세요."), `TERMS_VERSION` 값, 약관·개인정보처리방침 링크 주소(`/terms-of-service.html`·`/privacy-policy.html`)는 손대지 않는다. 접힌 상태에서도 **[필수] 동의 체크박스 자체는 항상 보여야 한다** — 접히는 것은 링크와 개인정보 처리 안내 설명뿐이고, 접힌 채로도 체크·제출이 가능해야 제출 검증 경로가 지금과 동일하게 유지된다. 웹(`src/pages/web/SignupScreen.jsx`)과 iOS(`ios/src/screens/Signup.tsx`)는 코드를 공유하지 않아 서로를 막지 않으므로, 두 이슈는 "기본 접힘 · 화살표로 펼침 · 펼친 내용과 문구는 현재와 동일" 이라는 눈으로 확인 가능한 동작 계약만 공유한다.
- [ ] **순서·검증** — 웹을 먼저 구현해 접힘 모양과 문구 배치를 확정하고, iOS가 그 결과를 그대로 맞춘다. 각 이슈는 (1) 화면 진입 시 접혀 있고 [필수] 동의 줄만 보이는지 (2) 화살표를 눌러 펼치면 약관 보기 링크와 개인정보 처리 안내 3줄, 개인정보처리방침 보기 링크가 지금과 같은 문구로 나오고 다시 눌러 접히는지 (3) 접은 채로 체크 후 제출이 되고, 체크하지 않으면 기존 오류 문구가 그대로 뜨는지 (4) 링크가 각각 약관·개인정보처리방침 페이지를 여는지 (5) 펼침 여부가 스크린리더에 전달되는지(웹 `aria-expanded`, iOS `accessibilityState`)를 확인하면 끝난 것이다. 두 화면을 나란히 놓고 접힘·펼침 모양이 같은지도 눈으로 대조한다.
- [ ] **재검토** — 앱 심사 대응이라 이번 범위는 이 화면 하나의 표시 방식뿐이다. 백엔드·새 의존성·공용 접힘 컴포넌트·다른 화면의 약관 표시는 추가하지 않는다. 웹은 브라우저 기본 접힘 요소로, iOS는 상태값 하나로 끝나는 분량이며, 재사용처가 두 번째로 생기기 전까지 공용 부품으로 빼지 않는다.
